# 消息表是对话记忆的唯一事实来源

改造前系统里并存两套互相矛盾的存储：LangGraph 的 `MemorySaver` 持有 agent 记忆（进程内，重启即丢），`data/sessions/*.json` 持有 UI 历史（落盘，但不含工具往返）。两者不是同一份数据，于是用户看得到历史记录，agent 却已经不记得了。

**决定：消息表是对话记忆的唯一事实来源。** 它存放完整的模型视角序列——用户消息、助手消息（含其发起的工具调用）、工具返回结果全部入表，每一轮从库里重建喂给模型的消息序列。UI 需要的「只看对话、折叠中间步骤」由查询时过滤实现，而不是靠不存。

**Agent 状态快照挂在运行上，只写不读。** evals 的回放层需要它，调试也需要它，所以它必须存；但它是观测数据，**不是恢复源**。系统里没有 checkpointer 语义：没有 resume，没有 time-travel，一次运行中途失败就是重来一轮，而不是从快照续跑。这条要写下来，是因为下一个读到快照的人几乎必然会想拿它恢复记忆——那正是被推翻的旧设计。

## 被否决的方案

**消息表只存对话层，工具往返只留在跨度里。** 表最干净、零内容重叠，但下一轮要无损重建记忆就得回头读观测数据，于是**观测数据变成不可丢的**，[ADR-0002](./0002-business-and-observability-share-a-database.md) 那条「观测失败不拖垮业务」当场作废。业务需要的东西，一样都不能只存在观测里。

**独立的检查点表作为恢复源。** 能精确恢复中断的运行，代价是重新引入两份可读数据，即本 ADR 要消灭的东西。中断续跑对一个公开 demo 不值这个价。

## 后果

- 消息按会话内显式 `seq` 排序，不靠时间戳——一次运行产出的多条消息时刻可能相同（旧 JSON 存档里 user 与 assistant 的 `timestamp` 就是完全一致的）。
- 「存了完整序列」不等于「每轮把完整序列喂给模型」。历史工具结果会让 prompt 迅速膨胀，如何截断或摘要是另一个决策；存下来只是保住了选择权。
