# 模型清单是发现来的，不是配置来的

现状把模型清单硬编码成 `backend/llm_config.py` 里的三个字典，代价已经兑现：`CLAUDE_MODELS["opus"]` 的值 `claude-opus-4-1-202508059` 日期段是 9 位、是个无效标识；`GROQ_MODELS` 整块被注释掉了而 `create_groq()` 仍在调它，一调必抛 `AttributeError`。而 `.get(model, 默认值)` 的写法让第一个错误静默回退，长期无人发现。

**决定：模型清单向端点档案实时发现，落库持久化，不硬编码任何清单——包括「兜底清单」。**

## 清单不等于可用集合

实测（2026-08-11，`api.ellisyuan.com`）：`GET /v1/models` 返回 49 个模型，其中至少三个调不通——`claude-3-5-haiku-20241022` 上游凭证冷却中、`grok-3-mini` 欠费（402）、`claude-fable-5` 缺额度（429）。发现接口不告诉你哪些真能用。

因此**不做可用性预探测**（那要对 49 个模型各发一次调用），也不在界面上承诺可用。选中一个调不通的模型，就按 [ADR-0015](./0015-upstream-errors-pass-through-unclassified.md) 把上游的话原样交回。这与「无效模型标识显式报错而非静默替换」是同一条精神：不预判，发出去，让上游说不行。

`模型清单`因此在术语表里定义为「可寻址的标识集合」而非「可用的模型」。

## 只吃一份清单，不吃协议专属的别名视图

这台中转站的两个协议返回**两份不同的清单**：OpenAI 格式给 49 个真名；Anthropic 格式给 16 个真 Claude 名 + 33 个把原名整串倒写、前缀 `claude-fable-5-dd-` 的别名（`claude-fable-5-dd-inim-4.5-tpg` 即 `gpt-5.4-mini`）。那套倒写是给只认 `claude*` 前缀的客户端准备的兼容视图。

交叉测试定了性：**真名在三个协议上通用**（`gpt-5.4-mini` 打 `/v1/messages` 得 200），**别名只在 Anthropic 端点有效**（打 `/v1/chat/completions` 得 502）。

Anthropic 格式那份清单元数据富得多（`display_name: "GPT 5.4 Mini"`、`max_input_tokens`、`max_tokens`），但要用它就得把「前缀 + 整串倒写」这条 **cliproxy 私有规则硬编码进代码**。**不要。** 只读 OpenAI 格式的 `/v1/models`，字段取 `id` 与 `owned_by`（后者正好给选单分组），显示名就用标识本身——对一个给工程师看的作品集，原始模型标识反而是更诚实的显示，它就是你要粘进请求里的那个字符串。

顺带一个不合规之处：该端点部分条目**缺 `created` 字段**，解析时不能假定它存在。

## 能力一概不探测

Anthropic 官方直连的 `GET /v1/models` 返回完整 `capabilities`——`effort` 逐档标记（`low`/`medium`/`high`/`xhigh`/`max`）、`thinking.types`、`structured_outputs`、`max_input_tokens`。**但经中转站一个都不透传**（实测该端点的 Anthropic 格式响应里 `capabilities` 字段为零），而本项目的实际部署正是走中转站。

做成「有时探得到、有时探不到」是最坏形态：同一个模型在直连与中转站下显示不同能力，用户只会当成 bug，而这个分支会渗进模型选单、努力档位切换器、API 契约三处。所以**只发现清单，不发现能力**；[努力档位](../../CONTEXT.md)照送（实测 `reasoning_effort: "xhigh"` 与 `parallel_tool_calls: false` 送给 `gpt-5.4` 均不报错），送了什么记进跨度，**生不生效是评测该回答的问题，不是配置该回答的问题**。

这同时推翻了一条早先记录：「OpenAI 的 reasoning 模型会忽略或拒绝 `parallel_tool_calls`」——至少经此中转站不拒。但「不拒绝」不等于「生效」，单次响应看不出来。

## 两层配置，两种生命周期

[两层密钥来源](../../CONTEXT.md)在发现这件事上表现为两套完全不同的节奏：

| | 服务端预设 | 用户自定义 |
|---|---|---|
| 何时拉 | 启动后自动拉，**24 小时自动刷新** | 用户填完 base URL 与密钥后**手动点击** |
| 过期 | TTL 24 小时 | 不过期，用户自己再点 |
| 落库 | **落库持久化** | **不落库**，只活在前端 |

超时统一 5 秒。拉取失败产生的是**提示性错误，不是中断性错误**——服务照常启动、照常服务，界面上明示「模型清单获取失败」并给出手填模型标识的输入框，标记 `source=fallback`。**自动刷新失败保留上一份清单**：模型列表变化很慢，丢掉一份大概率仍然有效的清单去换一个空选单是纯损失；返回体带上次成功拉取的时刻。

**兜底不是另一份清单，而是让用户手填标识。** 硬编码一份「备用清单」只会重蹈本文开头那个无效标识的覆辙。

## 为什么自定义端的清单不落库

本站全局公开、无鉴权。访客填进高级选项的 base URL 是他自己的中转站地址；连同「这台机器上有哪些模型」一起落进一个公共的库，等于把他的基础设施摊开给所有访客。

会话内容公开是[已定](./0013-the-session-list-shows-business-facts-only.md)且用户知情的（首屏明示）；把公开顺势扩张到用户填入的**接入配置**是另一回事。而「落库但按 base URL 隔离可见性」实质上是在一个明确不做鉴权的项目里搭一套隐式的归属维度，是那条范围边界的后门。

代价是用户每次开页面用自定义端点都要重点一次「下载模型」。在 demo 里这个代价很小。

## 后果

- `app` schema 新增一张模型清单表。它由发现任务写入、不由业务逻辑写入——这一点与 [ADR-0011](./0011-model-input-configuration-is-versioned-and-persisted.md) 那两张表同类，实现时须写明，否则下一个读到的人会想给它加一套 CRUD。
- 两个接口：`GET /api/models` 读库里的清单（带 `source` 与拉取时刻），`POST /api/models/refresh` 触发拉取（自定义端的「下载模型」走它）。
- 24 小时自动刷新需要一个后台定时任务，是本项目第一个此类组件。
- 响应回显的模型标识**可能不等于**请求发出的标识（送 `gpt-5.4-mini`，回 `gpt-5.4-mini-2026-03-17`）。跨度里记回显值。
- 上游响应夹带规范外的字段（`reasoning_content`、`native_finish_reason`、Anthropic 侧的 `caller` 与 `stop_details`）。解析时不得开启「多余字段即报错」。
