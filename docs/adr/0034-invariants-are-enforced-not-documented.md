# 可机械验证的不变量必须由检查器执行

仓库已经用 33 份 ADR 记录架构决定，也在 README 里画出模块依赖、目录结构和验证命令。但 ADR-0007 曾有四处依赖方向与实现不符：规则写进仓库解决了「不可见」，没有解决「会腐化」。

现有 `scripts/check-readme-ci-commands.sh` 已证明一条低成本路径：README 用 marker 标出派生内容，脚本把它与 CI 真源逐字比对；配套测试再主动注入漂移，确认检查器真的会红。

**决定：凡能从代码、配置或文件系统确定推导的不变量，不再依赖 Markdown 提醒，而由可执行检查器守护；文档只解释为什么，检查器负责判定现在是否仍然成立。**

首批适应度函数覆盖：

1. Import Linter 守护 ADR-0007 的能力模块依赖边界与无环性质。
2. `scripts/check-docs-drift.py` 从 AST 和文件系统生成 README 的 import 图、仓库树与 ADR 数量。
3. README 的 CI 命令继续由 `scripts/check-readme-ci-commands.sh` 与真实 workflow 对照。
4. 本地 pre-commit 提供快速反馈，CI 对完整仓库再次验证。

## 为什么不把所有 ADR 都写成 lint

架构决定分两类。模块依赖、文件计数、命令一致性有确定答案，适合做二值门禁；「这个抽象是否值得」「错误是否该原样透传」需要语义判断，硬写成正则只会制造误报和绕规则行为。

检查器的准入标准是：失败原因必须明确、结果必须确定、修复动作必须可执行。达不到这三条的仍由测试、评测或审查承担，不伪装成机械门禁。

## 已知代价

检查器本身也是代码，需要测试和维护。生成器与实现可能一起犯错，因此生成区块仍需在 PR 中正常审阅；它消除的是无意漂移，不替代设计判断。

Import Linter 增加一个开发依赖和一次静态扫描。当前包规模下耗时远低于后端测试，接受这项成本。

## 后果

- ADR 写「为什么」，配置和脚本写「怎么判定」；同一规则不在多个文档重复展开。
- 生成区块只通过 `--fix` 更新，手工编辑会在 pre-commit 或 CI 失败。
- 新增可机械验证的架构决定时，要么同时提供适应度函数，要么在 ADR 中解释为什么不适合机械化。
- 检查错误必须给出规则来源和可执行修复命令，让 Agent 能在同一轮自行纠正。
