# 长文档用渐进披露，不引入向量检索

一篇网页转成 Markdown 可能两万字，而回答问题需要的往往只是其中一小块。现状的做法是在工具内硬截断（`content[:3000]`）并对截掉的部分只字不提，模型据此可以理直气壮地说"文中未提及"。

**决定：`web_reader` 采用[渐进披露](../../CONTEXT.md)。** 向[工具供应商](../../CONTEXT.md)取回**全文**，在编排层按 Markdown 标题切成章节并计数：

- 全文在阈值内 → **直接全文返回**，不做任何加工。
- 超过阈值 → 返回**文档结构**（标题、全文长度、各章节编号与长度）加首节正文，并告知模型可用 `section` 参数索取指定章节。后续 `web_reader(url, section="3,5")` 返回对应章节全文。

首版阈值定为 8K token。**这个数字是拍的，不是算的**——网页 Markdown 化后的真实长度分布没有实测数据，应由评测用"章节选错率"与"答案完整率"去校准。

## 为什么不是硬截断

截断吃掉后半截而模型毫不知情，是现状最糟的一点。渐进披露下**全文始终在编排层手里**，模型想要哪节给哪节，零精简、零转述，读到的每个字都是原文。

即便走到必须截断的兜底路径（无标题层级的长网页，按段落聚合成定长块），也必须**如实标注**：`[内容已截断：全文约 21400 字符，以下为前 6000 字符]`。一行字符串的成本，换来模型知道自己看的是残卷,可以据此换 URL、换查询或在回答中说明。**宁可让模型知道自己无知，不可让它误以为自己全知。**

摘要是**由弱模型主导的有损压缩**。主模型看到的不是原文而是转述版，据此写出的引用对应不上任何一段真实原文——引用忠实度这项指标要么判它全错，要么被迫放宽到"大意相符"，而放宽之后指标本身也就废了。附带的代价是主模型永远无法找回摘要器丢掉的信息，且它连"有东西被丢了"都不知道。

同理，Tavily 的 `include_answer`（附送现成答案）与 `include_raw_content`（附送整页正文）一律关闭。前者让模型倾向于抄供应商的答案而非自己推理，轨迹与引用两类指标一起失真；后者把整页正文塞进检索结果，正好绕过本决策建立的机制。

## 为什么不是向量检索

需求成立，但方案是被超越的那个。[PageIndex](https://github.com/VectifyAI/PageIndex) 提出的 vectorless、reasoning-based 检索——生成文档结构树，让模型像人查书一样读目录、选章节、再读正文——在 FinanceBench 上取得 98.7%，而传统向量 RAG 约 50%。原因很直白：向量取回的是**语义相似**的片段而非**逻辑相关**的片段，且按固定 token 窗口切块会把一个论证从中间劈开。

本决策采用的正是这个范式：**按文档自身的语义结构切，而非按固定大小切**。"分页大小怎么定"这个问题的正解是不定——跟着标题层级走。

引入 embedding 与向量库还会同时撞上范围红线：地图已将 RAG / 文档问答划为 out of scope。

## 只做一级

[实测研究](https://arxiv.org/abs/2607.17598)比较了全文直读、混合 RAG、一级渐进披露与两级路由：单文档场景下，渐进披露的收益只在 agent 自身导航能力弱时才显著；多文档场景下全文直读**直接崩溃**，一级渐进披露明显胜出；**两级路由没有好处，有时反而更差**。

因此只做一级，且阈值宁高勿低——短文档强行进两段式只会白白多一次往返。

## 上下文窗口不是约束，上下文腐蚀才是

Opus 5 是 1M token 窗口，长上下文附加费已于 2026 年 3 月取消，塞进两万字毫无压力。真正的约束来自 [Context Rot](https://www.morphllm.com/context-rot)（覆盖 18 个模型）：性能**非线性**衰减，模型会撞悬崖而非缓慢变差；且**语义相似度比长度更致命**——干扰内容与答案越接近，准确率跌得越狠。

研究型 agent 恰恰是这个最坏情况：它读的五篇文章全部关于同一主题，干扰项与答案的语义相似度接近满值。"窗口够大就全塞"在本项目的场景下是最不该用的策略。

## 后果

**分节读取靠[运行](../../CONTEXT.md)内记忆化，不引入缓存层。** 以 URL 为键，活在一次运行的生命周期内，运行结束即死。它几乎零额外成本——[工具执行器](../../CONTEXT.md)本就需要一个执行上下文承载跨度上下文、共享的 HTTP 客户端与运行标识，记忆化只是其上多一个字段。**这不是缓存层**，跨请求缓存仍是未决问题。

**读取过程本身成为可观测的推理链。** 每次读取是一个独立跨度，前端会呈现出"检索 → 读结构 → 选第 3 节 → 再选第 5 节 → 作答"。这比"读了一大坨然后蹦出答案"更能展示 agent 的推理过程。
