# 工具是能力，供应商是可替换的实现

现状把横切逻辑焊死在工具类里：`SummarizingTavilyExtract` 继承 `TavilyExtract` 并覆写 `_run` / `_arun`，还得手动 `kwargs.pop('run_manager')`。后果是工具、供应商、摘要逻辑、UI 字段四者纠缠在一个类里，换任何一样都要动其余三样。

**决定：把[工具](../../CONTEXT.md)切成三层，只有最下面一层认识[工具供应商](../../CONTEXT.md)。**

| 层 | 职责 | 认识谁 |
|---|---|---|
| 契约层 | 名字、描述、入参 schema、给模型看的文本长什么样 | 只认识模型 |
| 编排层 | 规范化、切章节、数 token、判阈值、组装返回 | 谁都不认识，纯函数 |
| 端口层 | `fetch(url)` / `search(query, …)` 的抽象与各家实现 | 只认识供应商 |

第一版 `web_search` 走 Tavily、`web_reader` 走 Jina Reader。两者都只用供应商**最朴素的那个调用**：Jina 侧一个 `GET r.jina.ai/{url}`，它那批 `x-markdown-chunking` / `x-max-tokens` / `x-target-selector` 专有 header 一个都不用。这不是浪费——切分逻辑留在编排层是刻意的，Reader 侧按输出 token 计费 $0.02/1M，拿全文的代价可以忽略，没有任何理由把这项能力外包出去换取耦合。

## 横切逻辑归执行器，不归装饰器

**[工具执行器](../../CONTEXT.md)是调用工具的唯一入口**，超时、重试、错误分类、跨度记录、结果渲染全部集中在它一处。工具本身退化成一个干净的异步函数。

不用装饰器是因为它把责任推给了工具作者：贴漏了没人发现，`@retry` 与 `@timeout` 的堆叠顺序还改变语义。执行器则是结构上不可能漏——它是唯一入口，新加的工具自动获得全部横切能力。

各工具的差异（超时值、可否重试、可否并行）作为**注册元数据**挂在工具上，执行器读取后施加：**配置在工具身上，逻辑在执行器里**。这正是现状那个继承 hack 的精确反面——把横切逻辑从工具内部提到调用点。

## 工具定义只写一份

[协议](../../CONTEXT.md)有三种，工具字段的写法各不相同（Anthropic 叫 `input_schema`，OpenAI 两个协议各有各的包法），但三家的参数体都是 JSON Schema。

**决定：工具层只产出 `{名字, 描述, JSON Schema}`，三种协议的序列化交给 `ModelPort`。** 工具层不认识协议，`ModelPort` 不认识工具语义。加工具时不必管协议，加协议时不必管工具。

由此得到一条可写成测试的判据：**同一份工具定义序列化到三种协议后必须语义等价**。

## 一份结果，两个出口

工具返回有两个消费者，现状把它们混作一谈——`include_favicon` 开着，网站图标混在发给模型的内容里白烧 token。

**决定：工具返回结构化对象。** 对象原样进跨度供前端渲染（相关性分、favicon、供应商、耗时都用得上），由执行器渲染成纯文本进模型上下文（只有编号、标题、URL、摘要片段）。模型的上下文里不该出现一个 favicon URL。

## 并行按只读假设，并显式标注

[三种协议都支持模型在一轮里并发发起多个工具调用](https://zylos.ai/research/2026-04-07-tool-use-function-calling-standards-benchmarks/)，且业界只提供开关（`parallel_tool_calls` / `disable_parallel_tool_use`）而非计数。**默认开启并发，不设并发数上限。**

并发对同样的工作量严格更省：LLM API 无状态，串行每一步都要重发整个上下文。三次检索串行是 4 次模型调用、`4P + 6r` 输入 token，并行是 2 次调用、`2P + 3r`。加速另有实测支撑——agentic search 上扩展宽度可得约 4 倍加速，且同一轮内发出的调用是在同一次推理里一起想清楚的，模型能互相协调避免重复检索，这是串行拿不到的。

并发的真实风险是状态而非预算：隐藏依赖、共享状态竞争、写操作 race。当前两个工具都**只读无副作用**，正在安全区。因此在注册元数据里预留 `可并行` 标记，只读工具默认为真；将来任何有副作用的工具标为假，由执行器串行化。现在写这一行成本为零，将来漏掉则是只在并发下偶发的数据竞争。

## 后果

**工具 schema 允许随供应商演进，不做历史兼容。** 换供应商时若 schema 变化，旧[会话](../../CONTEXT.md)的[消息](../../CONTEXT.md)里会留下当前 schema 已不存在的参数——接受这一点，不做迁移层、不做兼容层。schema 变更仍应当作有版本的契约变更处理（记录并跑评测对比），但那是提示词版本化那条链路的事。

**换供应商保证换得动，不保证质量不掉。** 自研 reader 没有 JS 渲染（无头浏览器已被排除），碰上 SPA 站点大概率只拿到空壳。架构补不了能力差距——但端口抽象让"自研打头阵、失败降级到 Jina"这种组合实现变成一个几十行的装饰器。

**供应商差异会渗进 Markdown，咬到评测基线。** 不同实现生成的 Markdown 在标题层级、表格、脚注上不会逐字相同，而 Markdown 一变章节边界就变、章节编号就变。对策是在端口边界做一次本项目自己的 Markdown 规范化，把差异吸收在进入编排层之前。

**编排层用纯函数复用，不用继承。** 切分、计数、渲染写成模块里的独立函数，不是基类、不是插件框架。当前只有一个调用方，纯函数因此零成本；将来第二个工具需要，直接 import。用继承换扩展性正是现状那段代码的病根。
