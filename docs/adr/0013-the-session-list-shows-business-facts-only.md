# 会话列表只反映业务事实

[会话](../../CONTEXT.md)是全局公开共享的，没有归属维度——所有访客共用**同一个**列表，谁都能翻看谁的对话与 trace。这把两件在私有列表里无关紧要的事变成了硬约束。

**决定：会话随第一条用户消息诞生，且列表项只展示 `app` schema 内的字段。**

## 空会话不落库

旧前端点一次「新对话」就 `POST /api/sessions` 建一条记录。业界两家做法相反：LibreChat 只在**首条消息提交时**才落库，打开新对话不产生任何记录；Open WebUI 点 New Chat 就 `insert_new_chat`，靠「临时对话」模式开例外。

本项目只能选前者，理由不在优雅而在**噪音归谁**：Open WebUI 的列表是每用户私有的，多几条空会话只脏自己；本项目的列表是公共门面，每个路过的访客点一下就往上面塞一条空记录，脏的是所有人看到的第一屏。同一个设计在私有列表里是小瑕疵，在公开列表里是持续劣化。

**前端生成会话标识作为路由，第一条用户消息提交时后端 upsert 建会话。** 显式的 `POST /api/sessions` 从 API 契约里去掉。

由此得到一条不变式：**会话的存在性等价于"至少有一条消息"**。「空会话」不是一种状态，是不存在——列表因此不需要"过滤掉空会话"这条规则，它压根构造不出这种记录。这与 `CONTEXT.md` 里「会话是消息的容器」的定义一致：没有内容物的容器不是空容器，是没有容器。

## 列表项不显示 token 与成本

一个以可观测为卖点的项目，第一反应是把用量堆到列表上——每条会话跑了几步、烧了多少 token。**不做，而且理由是硬的**：那些数在 `obs` schema 里，而 [ADR-0002](./0002-business-and-observability-share-a-database.md) 的铁律是观测可丢、业务不可丢，外键只能 `obs → app` 单向。

会话列表是业务视图。它一旦显示 token，业务视图就反向依赖了观测数据——观测按 [ADR-0003](./0003-span-table-follows-phoenix.md) 分级老化清空 `attributes` 的那天，或者观测写入失败被吞掉日志的那天，列表就残缺了。而观测写入失败只记日志、不拖垮业务，恰恰是那条铁律换来的东西。让公共门面挂在可丢的数据上，等于把这笔交易反着做了一遍。

**列表项：标题、相对时间、消息数**——三项全在 `app` schema 内。用量、成本、步数只出现在 trace 面板，那里本来就是观测视图，数据老化后显示"已归档"是诚实的。

## 后果

- 会话标识由前端生成，形态（建议 UUIDv7）归数据模型决定。
- 列表按更新时间倒序，游标分页。
- 本次改造**不设任何鉴权**：任何访客可删除、可重命名、可在他人会话中续聊，不做站长下架口子、不做置顶、不做 fork。这是范围决定而非架构决定——身份验证与 RBAC 将作为独立 effort 另行开展，此处不为其预留抽象、不留 hook、不改接口形状。删除与重命名走 `conversation/service.py` → repository 是 [ADR-0007](./0007-backend-is-split-by-capability-not-by-layer.md) 已定的路径，将来加鉴权就是在 router 层多一道切缝的事。
- 软删除（`deleted_at`）保留，但理由变了。它当初的用途之一是"站长可恢复"，而本次不做站长口子；留着是因为**硬删会话会打断 `obs → app` 的外键**——观测数据指向的业务行不能凭访客一次点击消失。
