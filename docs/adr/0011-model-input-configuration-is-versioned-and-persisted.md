# 模型输入的配置面全部版本化落库

模型看到的东西只有三块：系统提示词、工具集 schema、对话消息。第三块已由[ADR-0001](./0001-messages-are-the-single-source-of-truth.md)的消息表兜住，前两块此前哪儿都没记——于是一次运行事后不可重建，而"改了提示词是变好还是变坏"只能凭感觉。

**决定：系统提示词与工具集 schema 各自一张不可变版本表，逐字存原文；[跨度](../../CONTEXT.md)只引用版本标识，不内联全文。**

两张表共有 `name` / `content`（逐字原文）/ `content_hash` / `created_at` / `version_id`。`prompt_versions` 另有 `variables`（这一版认哪些插值变量）；`tool_schema_versions` 另有 `effort_tier`。

**不合并成一张带 `kind` 列的宽表。** 两者的查询形态不同——工具集有档位维度而提示词没有，提示词有变量声明而工具集没有。合并立刻产出一半列恒为 NULL 的表，以及每条查询都要带的 `WHERE kind =`。

## 版本标识是内容的纯函数

`version_id` 取 `<名字>@<创建时间>-<内容哈希>`，哈希是逐字原文的 `sha256` 前 12 位。逐字相同则标识相同，逐字不同则标识必不同，**中间没有人为环节**。

**不用 git commit SHA。** 它标识的是整个仓库的状态，改一行 README 也会变。用它做版本，trace 里会堆出成千上万个"不同版本"而其中绝大多数提示词逐字相同，评测分组当场失效。

**不用人手维护的语义版本号。** 它依赖人记得改。一次忘记，就有两版不同的文本共用同一个标识——那正是本 ADR 要消灭的问题换个形式复活。

哈希不是人类友好的，所以标识里带 `name` 与 `created_at`：机器认哈希，人认名字和时刻。

## 为什么工具集 schema 也要落库

它看着像派生量——由代码里的定义加档位参数算出来，[ADR-0003](./0003-span-table-follows-phoenix.md) 刚立过"[推算](../../CONTEXT.md)不落库"的规矩。但那条规矩套不到这里，**两者的差别是能不能重算**：

成本可以事后重算，因为它的输入（token 数、模型名）是不变的[观测事实](../../CONTEXT.md)，变的只有价格表。schema **不能**事后重算——它只在构建那一刻等于代码的函数，运行发生之后代码继续演进，半年后拿今天的代码算不出当初那一份。

所以工具集 schema 是**事后不可变的观测事实**，与 token 数同类。不落库就是永久丢失。

## 粒度按工具集，不按工具

一个档位下全部工具定义的规范化有序 JSON 数组算作一个版本，跨度引用一个标识。

因为**模型看到的是工具集，不是单个工具**。工具之间的区分度、描述里的措辞会不会互相打架，都是集合层面的属性——[ADR-0004](./0004-tools-are-capabilities-providers-are-implementations.md) 判工具误选率指标死刑，用的正是一条集合层面的判断（两个正交工具下该指标恒为常数）。评测要归因的是"这套工具集表现如何"，跨度引用一个标识、跑分挂一个标识，切片才不用做集合运算。

代价：改一个工具的一行 `description`，四档全部产生新版本行。这恰恰是对的——它如实反映了"模型看到的工具集变了"。

## 跨度存指代，不存全文

跨度里那条模型调用的 system 消息内容，整块替换成字面量 `{system_prompt@<version_id>}`；同一标识另填进 OpenInference 的 `llm.prompt_template.version`，`llm.prompt_template.variables` 照填 `date` 与 `step_budget`。工具集同理。**前端原样渲染这个占位符，不提供展开。**

方向上这是 `obs → app` 的引用，正是 [ADR-0002](./0002-business-and-observability-share-a-database.md) 唯一放行的那个方向。若提示词存在库外（仓库文件），跨度就只能引用一个库外标识，引用完整性无从保证——落库反而比文件更贴合已有架构。

**版本表可运行时写入，代码层面不加限制。** 直接写库既没有操作面也没有攻击面（用户侧根本够不着），为它造一层只读护栏是给假想的问题加约束。

## 与 evals 的挂钩

**脱离 eval 的提示词版本化只是仪式**，所以这条是本决策的实质部分。

[ADR-0005](./0005-long-documents-use-progressive-disclosure.md) 所属的评测分级是"PR 只跑 L1+L2 零额度 · merge 触发小样本 judge · release 跑全量"。**提示词变更在 L1+L2 上没有信号**——L2 回放的是录好的模型响应，换了提示词响应就变了，回放答不出"新版更好吗"。按现行分级，改提示词的 PR 拿到的绿灯是假绿灯。

**因此为提示词与工具集变更在 PR 上开额度口子。** "PR 零额度"是为日常代码改动立的，那些改动本来就与模型行为无关；提示词改动是唯一一类除了烧额度拿不到任何信号的改动，为它开口子是这条原则的应有之义，不是破例。

**触发靠比对版本行，不靠 git diff。** CI 里"新版"是本次改动现算的哈希，"旧版"是表里 `created_at` 最新的那一行：哈希相同就跳过，不同就跑对比。判的是"模型看到的东西变没变"，比"文件动没动"准。

**基线在同一次 CI 里现跑，不缓存历史跑分。** 新旧两版用同一批数据、同一判官、同一档位各跑一遍。判官模型自身有抖动，隔天跑的数字不可比，拿它当基线是把噪声当成进步。代价是双倍额度，小样本下可以忽略。

## 后果

- 改一行工具 `description` 会触发烧额度的 eval。这是对的——[ADR-0004](./0004-tools-are-capabilities-providers-are-implementations.md) 明写"想引导就写进 `description`"，那 description 本来就是提示词，只是住在 schema 里。
- 两张版本表单调增长，只增不改不删。每行几 KB，一年也堆不出可观体积，且它同时就是"每个版本都有备份"这条要求的落实处。
- `app` schema 里出现两张不由业务逻辑写入的表——数据来自构建产物与启动同步。这个特殊性必须写明，否则下一个读到它们的人会想加一套 CRUD 接口。
- 任意一次历史运行的模型输入可以逐字重建，不依赖当时的代码、不依赖当时的 git 状态。这是"可复现"这条叙事的闭合点。
