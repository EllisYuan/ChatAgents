# 界面从不提及密钥

模型接入层定了**两层密钥来源**——服务端环境变量预设，加上前端高级选项里用户自己填的，用户填了优先用用户的。它同时给 [#18](https://github.com/EllisYuan/ChatAgents/issues/18) 交办了一件事：**「本次请求用的是用户自己的 key 还是服务端预设」要在界面上呈现**，理由是成本归属——用户用自己的 key，那笔钱算他头上；用预设则算项目方头上，两者混在一起成本面板就失去意义。

**决定：呈现层任何一层都不提及密钥——不显示密钥值，也不显示密钥来源。上面那条交办作废。**

## 三条理由

**一、没有金额就没有归属问题。** [ADR-0028](./0028-the-chat-surface-is-the-only-console.md) 把成本数字整个划出了当前阶段（价格矩阵仍是一片未毕业的雾），界面上只有 token 计数。token 不是钱，「这些 token 算谁头上」不是一个读者需要回答的问题。那条交办的全部论据是成本面板的可信度，论据的前提已经不在了。

**二、模型清单的拉取动作本身就是密钥的验证位。** 用户填完自定义端点与 key，下一步必然是选模型，而选模型之前要先拉清单（[ADR-0016](./0016-the-model-list-is-discovered-and-persisted.md) 定了清单运行时发现、自定义端手动点击下载）。**拉得到就说明 key 有效，拉不到用户当场就知道是自己的配置有问题。**验证已经在正确的地方发生过了，在对话流里再解释一遍是重复。

**三、公开站上「这轮是谁的 key」对访客不可行动。** 会话全局公开共享、无鉴权、任何访客可在他人会话里续聊。一个访客看到别人那轮用的是服务端预设，他也做不了任何事。

## 唯一保留：高级选项里的输入框

那是**输入位不是展示位**。两层密钥来源是既定约束，不归本决定推翻——用户必须能填自己的 key。填与不填这件事，面板本身就回答了。

## 失败态零例外

用户 key 调用失败时**只透传上游原文**，不附加「本次使用你填写的密钥」这类说明。

模型接入层定了用户 key 失败不静默 fallback，所以失败会如实暴露；[ADR-0015](./0015-upstream-errors-pass-through-unclassified.md) 定了上游错误原文透传不分类。加那句话等于把密钥来源从后门放回呈现层，而它换来的信息量为零——理由二已经让用户知道自己的 key 能不能用了。

**「不提密钥」是一条没有例外的规则。**一旦开一个失败态的口子，以后每出现一个新场景都要重新判一次「这算不算例外」，而判错的代价是密钥来源在某个没人预料的角落里露出来。

## 卫生要求照旧

密钥值绝不出现在跨度展示中——这条本就是模型接入层的硬要求，[#17](https://github.com/EllisYuan/ChatAgents/issues/17) 为它安排了一条必做的 CI 断言（跑一次运行后扫 `obs.spans` 的 `attributes` 不含密钥，且不能只跑 happy path，因为泄漏最可能发生在错误跨度里）。本决定不改变它，只是把范围从「不出现在跨度里」扩到「不出现在界面的任何一层」。

## 后果

- **后端不变**：仍按可观测性方案把 `key_source`（`user_provided` / `server_default`）记进跨度 `attributes`。它是观测事实，值得记；只是没有 UI 读它。
- **契约里那个扩展成员失去了消费者**：[ADR-0021](./0021-the-contract-has-two-sources.md) 一线定的 RFC 9457 错误体带三个扩展成员，其中「密钥来源」原本是给界面用的。留着无害（日志与调试仍能用），但实现时必须知道**前端不读它**；若始终没有第二个消费者，它是可以删的。
- 成本归属这件事退回数据层：需要时从跨度里按 `key_source` 分组查得出来，那是查询工作，不是界面工作。
