# 模型由用户选定，系统永不代选

票名叫「多模型路由与降级策略」。**前半截判否**：本项目不做任何自动路由，也不在失败时替换模型。「路由」一词在本项目退役——只有用户选定的[端点档案](../../CONTEXT.md)与模型标识，以及失败时的处置。

## 为什么不做自动路由

自动路由要成立，得先有可路由的维度，而三条都是空的：

- **按任务路由**需要「什么任务用什么模型」的判据，而本项目只有一个 agent、一种任务形态（研究型问答）。
- **按成本路由**是成本熔断的变体，而本次改造的既定立场是只追踪不限制。
- **按延迟路由**需要延迟基线，现在一条都没有。

叙事上它也是反的。自动路由让读者看到一个黑箱替他选模型；这个项目的卖点恰恰是把选择和账单摊开给人看。手动选 + trace 里逐次明账，展示力强于自动路由再事后解释「我为什么这么选」。

## 为什么失败时也不换模型

换模型会让「这次运行用的什么模型」变成「取决于当时哪个可用」。而[跨度](../../CONTEXT.md)的模型字段、[用量](../../CONTEXT.md)归属、评测回放的基线，全都建立在它是确定的之上——**可复现是这个项目的核心叙事之一**，降级链是拿它去换一个 demo 里没人需要的可用性（无 SLA、无真实流量、挂了刷新即可）。而且「降到哪」需要一串没有证据支撑的配置选择。

知道什么时候**不**加降级，本身就是比加了更值得展示的判断。

## 协议是端点档案的属性，不是模型的属性

实测（2026-08-11，`api.ellisyuan.com`，cliproxy）确认三件事：

- `gpt-5.4-mini` 打 `POST /v1/messages` 返回 200；
- `claude-sonnet-4-5-20250929` 打 `POST /v1/chat/completions` 返回 200；
- `Authorization: Bearer` 与 `x-api-key` 在两个端点上可互换。

也就是说「用哪个协议」与「用哪个模型」是两个正交选择，**不能从模型标识推断协议**。任何 `if model.startswith("claude")` 式的推断都是对某一家中转站的猜测，而「base URL 可自定义」是本项目的硬需求。

因此前端呈现的是**档案 + 模型标识**两个选择，服务端预设为同一个 base URL 配多份档案（协议各异），默认 `openai_responses`。

## 辅助角色只独立一个模型标识

[ADR-0012](./0012-the-auxiliary-model-never-writes-to-the-message-table.md) 定了 `main` / `auxiliary` 两个[模型角色](../../CONTEXT.md)。**两者共用同一份端点档案**——同协议、同 base URL、同鉴权——独立的只有模型标识。

理由是让「跨厂商意外调用」在结构上不可能，而不是靠配置纪律：既然辅助角色连 base URL 都不能改，它就不可能指向另一家。代价是「辅助模型指向另一个中转站」这条路径消失，而它从来没有人要过。

`auxiliary` 的模型标识未指定、或指定的标识不在当前[模型清单](../../CONTEXT.md)内时，回落为与 `main` 相同。**这次回落必须留痕**——作为跨度属性记下「指定的是 X，实际用了 Y」。现状 `backend/llm_config.py:71` 那句 `LLMConfig.CLAUDE_MODELS.get(model, ...["sonnet"])` 正是不留痕的活标本：无效标识 `claude-opus-4-1-202508059`（日期段 9 位）能长期潜伏没人发现，就是因为它悄悄回落了。一个用主模型价格生成的会话标题若在账上无从解释，恰是这个项目要照亮的那类隐形成本。
