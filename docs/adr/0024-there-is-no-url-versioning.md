# 不做 URL 版本化

几乎每个正经 API 都有 `/api/v1/`。本项目没有。

**决定：路径就是 `/api/...`，不带版本段。这是一个决定，不是忘了加。**

## 为什么不是「以后再说」

URL 版本化存在的意义是让**旧客户端在新后端上继续跑**。这个前提在本项目里不成立，而且是被前面的决策主动消灭的：

- [#11](https://github.com/EllisYuan/ChatAgents/issues/11) 定了前后端**同版本号、同一次发布**，一次 git tag 同时出厂。理由是独立发布需要维护前后端兼容矩阵与真正的 API 向后兼容，那在多团队灰度发布时值回票价，在单人单服务器场景下只生产没人读的 changelog。
- 前端是 Nginx 托管的静态资源，每次部署**全量替换**。用户刷新页面拿到的就是新前端。

所以「旧客户端」这个东西不存在。加 `/v1/` 只会得到一个永远是 1 的常量——它不区分任何东西，只是每个 URL 里多五个字符。

更要紧的是 #11 那句话：**契约不漂移最省力的保证就是前后端永远同版本出厂**。版本段的存在会暗示「这里可以有多个版本共存」，而那正是本项目用同版本发布换掉的复杂度。

## 已知代价

浏览器里可能存着旧前端的标签页，用户不刷新就发请求，打到新后端上。这时的表现是**当场报错**，而不是走一条兼容路径。

接受。公开 demo 上的后果是一次刷新，不是数据损坏。

## 后果

- 破坏性变更就是破坏性变更，靠同版本发布保证两侧一起换，不靠版本段并存。
- 将来若真要做多版本共存（例如身份验证那个独立 effort 之后开放外部调用），那是重画范围的时候的事，届时连带要重新决定的还有鉴权与兼容策略——不是在这里预留一个空的 `/v1/` 就能提前买到的。
