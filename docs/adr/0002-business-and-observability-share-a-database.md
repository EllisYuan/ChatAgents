# 业务app与观测obs同库分 schema，依赖方向单向obs → app

trace 是本项目的核心展示物，前端要在聊天界面里直接点开某条[消息](../../CONTEXT.md#对话)看它的执行细节，因此业务数据与观测数据必须能一次查完。但两者的失败语义正好相反：消息写失败等于用户的话丢了，必须报错；[跨度](../../CONTEXT.md#观测)写失败只是少一条观测，**不该拖垮业务**。

**决定：一个 PostgreSQL 实例，`app` 与 `obs` 两个 schema。** 物理同库保住跨表 join；逻辑分 schema 让边界在代码里可见，并给下面这条纪律一个物理提示——**观测写入走独立事务，失败只记日志**，绝不与业务写入同事务提交。

**外键只能 `obs` → `app`，单向。** 观测可丢、业务不可丢，一旦业务反向依赖观测，上面那条纪律就作废了。这条约束有个不显然的后果：**message表上不能有 `run_id`**。「这条消息属于哪次[运行](../../CONTEXT.md#对话)」只能从观测侧圈定——运行记录触发它的消息与产出消息的 `seq` 上界（一次运行产出的消息在[会话](../../CONTEXT.md#对话)里必然连续）。

## 为什么是 PostgreSQL 而不是 SQLite

多个访客同时跑 agent，每次运行在流式过程中不断落跨度，SQLite 的单写者模型并发性能不好，缓解不了写写冲突。

## 访问层

SQLAlchemy 2.0 声明式 ORM（`Mapped[]` 注解，与项目的 mypy 档位相配）+ Alembic 迁移（`include_schemas` 同时管两个 schema）+ psycopg3 驱动。

## 删除语义

[会话](../../CONTEXT.md#对话)删除是**软删除**（`deleted_at` 标记），查询默认过滤。
