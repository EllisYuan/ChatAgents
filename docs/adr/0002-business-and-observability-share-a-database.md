# 业务与观测同库分 schema，依赖方向单向

trace 是本项目的核心展示物，前端要在聊天界面里直接点开某条消息看它的执行细节，因此业务数据与观测数据必须能一次查完。但两者的失败语义正好相反：消息写失败等于用户的话丢了，必须报错；跨度写失败只是少一条观测，**不该拖垮业务**。

**决定：一个 PostgreSQL 实例，`app` 与 `obs` 两个 schema。** 物理同库保住跨表 join；逻辑分 schema 让边界在代码里可见，并给下面这条纪律一个物理提示——**观测写入走独立事务，失败只记日志**，绝不与业务写入同事务提交。

**外键只能 `obs` → `app`，单向。** 观测可丢、业务不可丢，一旦业务反向依赖观测，上面那条纪律就作废了。这条约束有个不显然的后果：**消息表上不能有 `run_id`**。「这条消息属于哪次运行」只能从观测侧圈定——运行记录触发它的消息与产出消息的 `seq` 上界（一次运行产出的消息在会话里必然连续）。

## 为什么是 PostgreSQL 而不是 SQLite

token 面板的查询是分析型的——按模型、按[模型角色](../../CONTEXT.md)、按时间窗聚合用量并剔除 `PARTIAL`。更要紧的是流式期间是**持续写入**而非偶发写入：多个访客同时跑 agent，每次运行在流式过程中不断落跨度，SQLite 的单写者模型在这里是真实摩擦——WAL 能缓解读写冲突，缓解不了写写冲突。

代价如实记下：多一个运维对象与故障点，CI 需要真库而非内存库（这是交给测试策略决策的新负担）。

## 访问层

SQLAlchemy 2.0 声明式 ORM（`Mapped[]` 注解，与项目的 mypy 档位相配）+ Alembic 迁移（`include_schemas` 同时管两个 schema）+ psycopg3 驱动。

选 psycopg3 而非 asyncpg，是因为**一个驱动同时供 sync 与 async**：迁移、测试夹具、临时脚本走 sync，应用走 async，依赖树里只有一个东西；asyncpg 更快但纯 async，且停在 0.x、发版节奏明显放缓。**psycopg3 是 LGPL-3.0-only**——本项目动态导入、不二次分发、不闭源，relink 义务落不到实处，但许可证性质在此如实记录。

SQLModel 未纳入考虑：做了多年仍是 `0.0.39`，不满足地基层「选经过大规模生产验证的」判据。

## 删除语义

会话删除是**软删除**（`deleted_at` 标记），查询默认过滤。因为 demo 无鉴权、会话列表全局公开共享，任何匿名访客都能触发删除；硬删除只有两条路且都难看——级联会连 trace 一起销毁（核心展示物被路人一键抹掉），置空则留下一堆查不到上下文的孤儿跨度。
