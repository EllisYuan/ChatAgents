## Problem Statement

用户希望主 Agent 专注于回答问题，而不是为了生成会话标题继续保持运行中状态。当前标题生成虽然通过 auxiliary 模型调用完成，但仍与主运行共享生命周期、事件流和收尾逻辑。主回答已经完成或失败时，仍可能等待标题；标题用量也会混入回答的摘要行，难以区分回答和 metadata 各自的开销。

对维护者而言，标题任务的轮询、超时和收尾散落在 ReAct Loop 的多条退出路径中。新增一种主运行终止方式时，需要额外记住标题收尾协议，容易遗漏。仅抽取一个辅助方法不能满足用户要求的生命周期独立。

会话还必须具备可靠的基础行为：模型标题失败时仍有可识别的 fallback；人工改名不能被迟到结果覆盖；重复调用不能反复消耗模型；辅助调用的实际模型、用量和失败情况不能因为拆分而消失。

## Solution

将标题生成改为会话级的独立能力。首条用户消息保存时立即建立会话和 fallback 标题；前端收到首次运行的 `RUN_STARTED` 后，通过独立 HTTP 调用尽早生成模型标题，不等待主回答完成。标题只概括服务端保存的首条用户消息，固定使用 `effort="low"`，模型调用总超时默认 30 秒。

主运行和标题分别完成、失败和取消。停止回答不取消标题；切换会话或离开页面会取消尚未完成的标题调用。标题采用 best-effort，每个新会话至多一次自动生成尝试，失败、超时或取消后保留 fallback，不因刷新或后续消息重新调用模型。

新主运行的摘要行和 Trace 只反映主处理。标题观测独立归属会话，在会话标题附近提供轻量的“标题生成详情”入口，显示实际模型、用量、耗时、失败情况以及生成结果是否应用。历史标题和旧跨度保持原样，通过只读兼容方式展示，不重新调用模型或改写历史时间。

## User Stories

1. 作为会话用户，我希望主回答完成后立即结束主运行，以便不为标题生成继续等待。
2. 作为会话用户，我希望主运行失败时立即得到主运行的失败结果，以便标题耗时不会延迟我处理问题。
3. 作为会话用户，我希望首条消息保存后就有 fallback 标题，以便模型尚未响应时也能识别会话。
4. 作为会话用户，我希望标题在会话建立后尽早与主回答并发生成，以便不必等完整回答才看到有意义的标题。
5. 作为会话用户，我希望标题只概括首条用户消息，以便标题内容不依赖助手回答是否成功。
6. 作为会话用户，我希望后续追问不会自动改变标题，以便会话标识保持稳定。
7. 作为会话用户，我希望标题使用发送首条消息时选定的辅助模型与客户端配置，以便后来修改界面配置不会影响已经发起的处理。
8. 作为会话用户，我希望标题保留现有模型选择规则，以便拆分不会偷偷更换模型、端点档案或密钥。
9. 作为会话用户，我希望标题固定使用较低的努力档位，以便主问题的 `xhigh` 设置不会同时提高标题调用强度。
10. 作为会话用户，我希望标题调用有明确的 30 秒总超时上限，以便异常缓慢的调用不会无限持续。
11. 作为会话用户，我希望标题模型不可用、返回空文本或超时时保留 fallback，以便仍能继续使用会话。
12. 作为会话用户，我希望标题失败不会出现在主回答错误区，以便不会把 metadata 失败误认为回答失败。
13. 作为会话用户，我希望点击“停止回答”只停止主 Agent，以便已经发起的标题生成可以独立完成。
14. 作为会话用户，我希望切换会话或离开页面时停止尚未完成的标题调用，以便不继续进行不需要的模型调用。
15. 作为会话用户，我希望离开后到达的响应不会污染新打开的会话，以便界面状态始终对应正确的会话。
16. 作为会话用户，我希望刷新页面或重新进入会话不会重新生成标题，以便不会因为普通导航重复产生模型调用。
17. 作为会话用户，我希望标题失败、超时或取消后不自动再次尝试，以便调用次数和资源使用可以预期。
18. 作为会话用户，我希望多标签页或重复 HTTP 调用至多发起一次模型调用，以便不会被重复计费。
19. 作为会话用户，我希望清空或改回标题也不会重新开放自动生成，以便人工操作不产生隐含的模型调用。
20. 作为会话用户，我希望在模型调用前已经人工改名时直接跳过生成，以便不再为已经决定的标题调用模型。
21. 作为会话用户，我希望生成过程中人工改名始终优先，以便迟到的模型结果不能覆盖我的选择。
22. 作为会话用户，我希望相同文字、清空后改回 fallback 等改名操作也受保护，以便系统不会仅凭字符串相等误判为没有人工修改。
23. 作为会话用户，我希望模型成功但标题未应用时能看到准确原因，以便不会把人工改名保护误认为模型故障。
24. 作为会话用户，我希望删除会话后迟到的标题结果不能恢复它，以便删除操作不会被后台结果抵消。
25. 作为会话用户，我希望标题 HTTP 响应表示实际生效的标题，以便界面不会显示未成功保存的候选文本。
26. 作为会话用户，我希望数据库和界面都防止迟到结果覆盖人工改名，以便保存正确时界面也不会暂时显示错误标题。
27. 作为会话用户，我希望新回答下方的 token 只统计该主运行，以便准确理解回答本身的模型用量。
28. 作为会话用户，我希望新主运行的耗时不包含等待标题的时间，以便摘要行和实际回答结束时间一致。
29. 作为会话用户，我希望标题稍后完成时不会改动已结束回答的摘要数字，以便运行统计稳定且可解释。
30. 作为会话用户，我希望在会话标题附近查看标题生成详情，以便不必到某条回答的 ReAct 跨度树里寻找 metadata 调用。
31. 作为会话用户，我希望标题详情显示实际模型、努力档位、token 和耗时，以便辅助调用的开销保持透明。
32. 作为会话用户，我希望详情区分成功、失败、取消、未应用和无观测记录，以便不会把缺失记录误当成成功。
33. 作为会话用户，我希望未知用量不显示为零，以便不会低估实际发生的模型调用。
34. 作为会话用户，我希望打开或刷新标题详情只执行查询，以便查看观测不会额外调用模型。
35. 作为会话用户，我希望观测加载或写入失败不影响标题和聊天，以便辅助观测故障不会拖垮业务。
36. 作为会话用户，我希望侧边栏常驻列表保持简洁，以便只有主动打开详情时才看到标题调用的观测信息。
37. 作为使用自定义端点的用户，我希望密钥不会因新增标题调用而被持久化、打印或展示，以便接入信息保持私密。
38. 作为 API 调用方，我希望只调用主运行 Interface 时不会隐含启动标题模型，以便明确控制是否需要辅助调用。
39. 作为历史会话的用户，我希望升级后已有标题不被修改或重新生成，以便现有会话保持稳定。
40. 作为历史会话的用户，我希望新详情入口仍能读取旧标题跨度，以便拆分后不丢失已经存在的观测。
41. 作为历史会话的用户，我希望旧运行保留真实统计口径并明确标识，以便系统不会反推出一份未经记录的纯主运行耗时。
42. 作为历史会话的用户，我希望缺少旧观测时明确显示无记录，以便不会看到补造的模型、用量或错误原因。
43. 作为维护者，我希望 Agent Loop 的 Interface 不再包含标题职责，以便新增主运行退出路径时无需同时维护标题收尾协议。
44. 作为维护者，我希望一次性认领不依赖观测记录或单进程内存，以便并发和观测故障不会导致重复模型调用。
45. 作为维护者，我希望通过稳定的外部 Interface 验证行为，以便重构内部方法、任务调度或文件布局时测试仍然有效。
46. 作为维护者，我希望架构文档、契约与迁移兼容性随实现一起更新，以便后续维护者不会把本次有意调整当作架构违规再改回去。

## Implementation Decisions

### 领域语义与 Module 职责

- “运行”收窄为用户消息触发的主 ReAct 处理，标题生成不再属于其生命周期。标题生成是会话级 auxiliary 调用，不是另一条 ReAct 运行。
- 跨度可以归属主运行，也可以作为独立标题跨度归属会话；不再假定每个跨度必须拥有主 `run_id`。
- `main` / `auxiliary` 的判据继续是输出去向。标题只更新会话 metadata，永不写入 `app.message`。
- `AgentRunner` 移除标题专用参数、模型调用、prompt、fallback、任务轮询和收尾职责。主运行的事件、业务持久化、观测包装与 SSE 编码不再维护标题生命周期。
- 标题的业务规则归会话 Module，模型访问复用 `ModelPort`。LLM Module 不承载会话标题业务，业务 Module 不反向依赖观测 Module。
- 在现有 HTTP 装配层连接会话业务与独立观测包装，继续遵守单向依赖和独立事务规则。不建立通用 auxiliary 插件框架或只有单一实现的空抽象层。
- 独立性约束控制流、失败传播与终态，不承诺两条调用在共享上游、数据库或网络下完全没有资源竞争。

### HTTP Interface 与客户端编排

- 保留 `POST /api/runs` 的 AG-UI over SSE 主 Interface。保存首条用户消息时仍同步建立会话与 fallback，不新增空会话创建流程。
- 新增 `POST /api/sessions/{session_id}/title`，负责认领、生成、条件保存并返回普通 JSON。前端在首次运行的 `RUN_STARTED` 后尽早调用，不能等待主回答完成。
- POST 从服务端保存的首条用户消息读取素材；不接受客户端重新提交的标题素材、完整历史、`force`、重新生成或标题 `effort` 选项。
- POST 使用发送首条消息时的客户端配置快照，并返回 `session_id`、实际生效的 `title` 及业务处理结果。结果需区分已应用、保留 fallback、正在生成、已处理或不符合条件、人工改名导致未应用。
- 重复 POST 返回当前业务状态，不再调用模型，也不要求等待最初的 HTTP 调用完成。
- 新增 `GET /api/sessions/{session_id}/title-generation` 作为只读观测 Interface，供会话层详情消费；查询绝不认领、生成或重试。
- 标题业务响应不混入观测 token 或 Trace 数据，观测查询不读取业务 `title` 来推断模型是否成功；客户端合并业务与观测数据。
- 新主 SSE 不再发送 `chatagents.title` 或标题对应的 auxiliary 用量、跨度。主运行错误与标题错误各自在自己的 Interface 表达。
- 输入校验、会话不存在或已删除、业务存储失败继续使用现有错误契约。正式字段、枚举与状态码由后端类型统一定义并通过 OpenAPI 生成，前端不维护类型副本。
- 仅调用主运行 Interface 的客户端只得到 fallback；模型标题不是主运行的隐含保证。

### 模型配置、超时与失败

- 复用 `ModelOverride`、`resolve_profiles`、`EndpointProfile` 及三协议 Adapter。沿用现有辅助模型选择与来源留痕规则，不新增模型槽位、端点配置体系或自动换模型逻辑。
- 客户端快照固定于首条消息发送时，不在异步触发标题时重新读取当前界面配置。服务端预设仍按现有机制解析，不新增跨 HTTP 调用的配置版本恢复设施。
- 标题固定 `effort="low"`，即使主运行为 `xhigh` 也不改变；默认总超时 30 秒，从标题模型调用开始计时。
- 超时后取消并回收模型调用，保留 fallback，不留无人管理的任务。上游失败、空输出和缺少终态结果采用相同的业务降级原则，不导致主运行失败。
- 集中复用现有 fallback、标题 prompt 和长度约束；不在本次顺带调整标题内容策略。
- 业务存储失败由标题 HTTP 调用报告，不能装成成功。观测写入失败只降低可见性，不能影响业务更新或触发第二次模型调用。
- 用户密钥不新增服务端持久化或共享缓存，不能改用另一份密钥继续调用。日志、错误记录和观测载荷不得泄漏密钥或完整 `ModelOverride`。

### 一次性认领、人工改名与取消

- 每个新会话至多一次自动生成尝试。合法调用被原子认领后，成功、失败、超时、取消或未应用结果都不重新开放自动生成资格。
- “一次”是上限而非交付保证。页面可能在标题调用发出前关闭，允许从未调用标题模型并一直保留 fallback；刷新、重新进入、继续发送消息或查看详情均不补发。
- 在 `app` 保存最小持久化认领状态及人工改名保护信息。认领必须跨标签页、跨进程有效，不能只用进程锁，不能以 `obs.span` 是否存在判断是否已调用。
- 认领和条件应用使用短事务，模型调用期间不持有数据库事务、行锁或请求级连接。不引入 lease 接管、后台调度或恢复语义。
- 人工改名在模型调用前已发生时跳过调用；发生在调用期间时允许模型完成，但条件更新不得应用生成结果。
- 保护依据是明确的修改状态或版本，不是 `title == fallback`。相同文字、清空、改回原文都不能绕过保护或重置生成资格。
- POST 返回实际生效的业务标题；前端同时保护后续人工改名与当前会话状态，防止旧响应覆盖新状态。
- 会话软删除后不接受新生成，迟到结果不能恢复会话或更新已删除的 `title`。
- 主运行与标题使用独立取消控制。主运行完成、失败或用户停止回答不取消标题；离开会话或页面时取消标题，并在服务端处理 HTTP 断连、传播取消到模型调用和资源收尾。
- 取消不能撤销已产生的 token 或已提交的 `title`；取消与提交竞争时按实际结果记录，不自动重试。
- 正常失败、超时和取消应尽力记录终态；进程强制退出或观测写入失败时不保证完整记录，不伪造成功、不后台恢复。

### 观测归属、统计与前端详情

- `obs.run` 继续表示主 Agent 运行，不新增标题专用的伪 ReAct 运行或 `kind=title` 分支。
- 扩展 `obs.span` 的归属：新标题跨度通过 `session_id` 独立关联会话，不依附主 `run_id`，且作为根跨度存在。数据库约束必须保证归属明确，不允许同时归属主运行与独立会话或完全没有归属。
- 复用现有跨度的物化用量字段、用量三态与保留策略。记录实际 `model`、`role="auxiliary"`、`effort`、协议、模型解析来源、时间、用量及实际结果。
- `usage_status` 仍只有 `complete` / `partial` / `unavailable`。没有事实时不填 0；取消不等于一定存在可估算 token；`reasoning_tokens` 是 `output_tokens` 的子集，总量不重复累加。
- 模型调用结果与标题应用结果分别表达。模型成功、用量完整但因人工改名未应用，不能被标为模型调用失败。
- `key_source` 可继续作为后端观测事实保存，但前端不展示密钥值或来源。
- 会话标题附近提供轻量的“标题生成详情”入口，展示实际模型、努力档位、用量、耗时、失败情况和应用结果。常驻列表不加入观测指标。
- 详情通过普通 JSON 与按需只读查询更新，不新增标题 SSE 或常驻后台轮询。观测查询失败只影响详情，不阻塞聊天或标题展示。
- 未闭合记录不代表任务必然仍存活；无记录、未完成记录和真实失败要如实表达，不能把残留记录无限显示为可靠的生成中状态。
- 新主运行的摘要行、实时 Trace、REST 统计和 `obs.run.ended_at` 都排除标题调用；标题稍后完成不能再回填第一条回答的统计。

### 历史数据、迁移与架构记录

- 旧会话初始化为不会自动补发的历史状态，不能因新增字段默认值而重新获得生成资格。
- 不修改历史 `title`，不重新调用模型，不迁移旧标题跨度，不改变其 `run_id`、`parent_span_id` 或 `ended_at`。
- 新详情入口兼容读取旧 `name="title_generation"`、`role="auxiliary"` 的跨度。缺少模型、用量、原始候选文本或错误原因时只展示已有事实，不根据当前标题反推。
- 历史主运行保留原统计口径，明确可能包含标题用量和等待时间；不反推未经记录的纯主运行耗时。
- 扩展独立跨度时检查所有依赖 `run_id` 必填假设的读写、统计和观测保留路径，不只修改 ORM 标注。
- 迁移不删除旧数据，不依赖 downgrade。必须核对放宽 `run_id` 假设及新增归属约束对旧代码、新 schema 的兼容性；不能静默绕过迁移纪律。
- 实施时显式替代 ADR-0012 中标题与主运行共用生命周期的决定，保留 auxiliary 不写消息表等约束；同步调整运行与跨度的领域定义、相关 Module 架构说明、观测与事件约定、前端 Trace 规范和生成契约。

## Testing Decisions

### 测试 seam

- 以应用的 HTTP Interface 为主要外部测试 seam：通过主运行、标题生成、人工改名、会话查询和观测查询验证用户能够观察到的行为。优先从这一处证明完整流程，避免分别 mock 每一层后只证明内部方法被调用。
- 复用现有 `ModelPort` 作为外部模型依赖的替换 seam，注入可控 Adapter；它是测试输入控制点，不是另一套产品 Interface。模型调用使用假实现，不消耗真实模型额度。
- 认领、并发、条件更新、软删除及 schema 约束使用真实 PostgreSQL 和独立连接验证，不用内存 repository 模拟数据库竞争。
- 前端补充页面或应用级的可见行为测试，控制 HTTP/SSE 输入，覆盖用户停止、导航、改名和打开详情；不依赖内部 hook 状态、组件私有实现或文件布局。
- 仅对高层测试无法清晰定位的规则补充窄测试。已有 AgentRunner 事件测试继续验证主 ReAct 行为，不为每个内部 helper 新建一个测试 seam。

### 好测试的标准

- 断言公开响应、可见状态、领域产物和真实持久化事实，不断言私有 task 名称、内部调用顺序或某个布尔变量。
- 用可控事件、屏障或时钟安排 main/title 的完成顺序、超时和取消，避免以脆弱的真实等待时间判断并发正确性。
- 分别证明模型调用是否发生、生成结果是否应用、观测是否可用；三者不能互相代替。
- 测试代码重构后仍成立，并同时覆盖成功和失败路径。不能把人工检查或未执行的测试清单描述为已通过测试。

### 必须覆盖的行为

1. 主运行正常完成、上游失败、缺少终态、触达硬上限和工具程序错误时，都不等待标题。
2. main 先完成和 title 先完成都正确；主事件流没有标题数据，新主统计不包含标题用量或等待时间。
3. 标题只读取服务端首条用户消息，不读取助手回答、不写消息表、不接受客户端替代素材。
4. 标题使用发送时的客户端配置快照、实际辅助模型和固定 `low`；修改界面配置不会影响已发起处理。
5. 总超时以模型调用开始为基准，默认 30 秒；超时、空输出、无终态和上游失败保留 fallback，不失败主运行。
6. 同会话并发 POST、多个独立连接或重复调用至多请求模型一次；成功、失败、取消、超时和未应用后都不重新调用。
7. 刷新、重新进入、后续消息、清空标题和详情查询都不补发标题生成。
8. 人工改名发生在调用前、调用中、结果保存后但响应到达前时，数据库与前端均正确保护人工结果；覆盖相同文字和改回 fallback 的场景。
9. 会话删除与生成并发时不会恢复会话或更新已删除的标题。
10. 停止主回答不取消标题；导航或关闭页面取消标题。除客户端中止外，还验证服务端传播断连取消、模型调用终止和客户端资源回收。
11. 取消与提交竞争时不撤销已提交结果，不制造虚假成功或零用量，也不留下脱离生命周期的异步调用。
12. 观测写入故障不影响业务更新，不使生成资格重新开放；业务写入失败不能返回虚假成功。
13. 模型成功但人工改名导致未应用时，模型状态、用量与应用结果分别正确记录和展示。
14. 新标题跨度只关联会话，不进入主运行列表或跨度树；schema 约束防止无归属或双重归属。
15. 标题详情可访问，缺失、失败、取消和未应用结果准确呈现；查询失败不影响聊天，未知用量不填零。
16. 密钥不出现在业务数据、观测、日志或 UI，成功和错误路径都覆盖；UI 不展示密钥来源。
17. 旧标题与旧跨度可读、原时间和统计口径不改写；没有旧观测时不补造记录，迁移不会使历史会话重新生成。
18. 新契约经过 OpenAPI 生成与契约测试，Module 依赖和迁移兼容满足项目门禁。

### 现有测试先例与完成标准

- 沿用现有进程内 FastAPI 契约测试，通过依赖替换控制模型输入与输出。
- 沿用现有 AgentRunner 注入 `ModelPort` 的测试方式，复用辅助模型成功、失败与实际模型留痕的测试意图。
- 沿用现有标题持久化的 PostgreSQL 测试，保留“标题保存但不产生 auxiliary 消息”的断言，并扩展到认领和人工改名竞争。
- 沿用现有 SSE 编码、观测故障隔离、密钥卫生及历史 Trace 合并的验证方式；旧标题事件测试迁移为新 Interface 的行为测试，不保留一套已经不存在的新主运行标题协议。
- 实施完成必须通过项目完整确定性检查，包括依赖方向、契约生成、文档防腐、后端测试与前端门禁。带方差的 Agent Evals 不替代确定性门禁，本 spec 不要求新增真实模型调用。

## Out of Scope

- queue、worker、outbox、后台调度、lease 接管、崩溃恢复和可靠最终完成保证。
- 自动重试、手动重新生成标题、后续主题变化自动改名、根据助手回答生成标题。
- 标题专用 SSE、常驻后台轮询、新模型槽位、新端点配置体系或标题努力档位 UI。
- 自动切换模型或密钥，以及跨两次 HTTP 调用恢复服务端旧配置版本的设施。
- 独立 dashboard、金额成本面板和新增鉴权体系。
- 批量重新生成历史标题、迁移旧标题跨度、重写历史时间或反推未记录统计。
- 无关 Issue 的修复、覆盖当前工作区既有修改、提前修改实现、自动 git commit 或 push。
